双击项目根目录的 `package.cmd` 即可重新编译当前代码、收集运行依赖、生成便携 ZIP 和 SHA256 校验文件。窗口最后会显示结果，按任意键关闭。

输出位置是项目根目录的 `dist`。发送最新的 `TraceReel-版本-windows-x64-时间-portable.zip` 给朋友；朋友完整解压后双击 `TraceReel.exe`。程序版本自动取自 Cargo 配置，每次打包创建独立目录。

构建使用 `target/package-build`，不会覆盖 `target/release` 中正在运行的程序。MSVC x64 运行库自动查找；Qt、FFmpeg 和 libclang 默认沿用本机已有构建环境。

首次遇到旧版迁移过的构建缓存时，脚本会自动清理并重新编译本地 Rust 模块，保留第三方依赖缓存。OCR 源码和发布 ZIP 的 SHA256 使用 .NET 计算，不依赖 `Get-FileHash` 命令。

也可以在 PowerShell 中运行：

```powershell
.\package.ps1
```

如果已经编译好、只需要重新收集依赖和压缩：

```powershell
.\package.ps1 -SkipBuild
```

依赖安装位置改变时，可以传入路径（传入的 Qt 和 FFmpeg 路径同时用于编译和打包）：

```powershell
.\package.ps1 -QtRoot 'C:\Qt\6.8.2\msvc2022_64' -FFmpegDir 'D:\ffmpeg-dev' -CrtDir 'C:\path\to\Microsoft.VC143.CRT'
```

可以用 `LIBCLANG_PATH` 环境变量指定 libclang 目录。缺失构建工具或运行依赖时，脚本报错并停止，不会报告打包成功。

## GitHub Actions 自动打包与发布

[Windows package and release](https://github.com/WaterFishJ/tracereel/actions/workflows/release.yml) 会在 `main` 的程序、依赖或打包配置变化时自动运行，也可以在 Actions 页面点击 **Run workflow** 手动运行。

工作流使用 Windows Server 2022、Rust stable、Qt 6.8.2 与固定版本的 FFmpeg 8.1 GPL shared 构建。自动下载并校验 FFmpeg 和 OCR 资源，运行逻辑测试，再调用仓库的 `package.ps1` 构建便携包。随后解压 ZIP，验证 GUI 能启动、运行库来自包内，并测试 FFmpeg 编解码。

普通分支构建的结果保存在该次运行的 **Artifacts** 中，保留 14 天，包括便携 ZIP、含 Gyroflow 子模块的完整项目源码 ZIP，以及各自的 SHA256 校验文件。

正式发布时：

1. 更新根目录 `Cargo.toml` 的 `[workspace.package] version`，并更新 `Cargo.lock` 和 `CHANGELOG.md`，提交并推送。
2. 确认该提交的打包工作流成功。
3. 创建与 Cargo 版本一致的标签并推送，例如版本已改为 `0.2.2` 时：

```powershell
git tag -a v0.2.2 -m 'TraceReel 0.2.2'
git push origin v0.2.2
```

推送 `v*` 标签会自动构建，只有测试与便携包验证通过后才会创建 GitHub Release，并附上便携包、对应源码和校验文件。标签必须严格匹配 Cargo 版本；带预发布后缀的版本（例如 `v0.2.1-beta.1`）会标记为 Pre-release。

发布使用 GitHub 自动提供的 `GITHUB_TOKEN`，不需要添加个人访问令牌或 Qt 账号。重跑同一标签时会更新对应 Release 的产物，不必重新创建标签。

可选的解压验证：

```powershell
.\packaging\verify-package.ps1 -Zip 'D:\path\to\TraceReel-portable.zip'
```
