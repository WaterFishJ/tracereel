# TraceReel Rust 防抖：全部问题与修复总结（防回归手册）

> 本文档记录从「防抖集成」到「预览与导出观感一致」过程中踩过的所有坑、根因与修复，
> 以及每一处“绝对不能再改回去”的关键点。修改 `app/src/gyro.rs`、`app/src/gui.rs`、
> `app/src/pipe.rs`、`app/src/settings.rs` 之前请先读本文档。
>
> 最终验收结论：预览与导出的平滑四元数逐帧一致（最大差 0.0002°），渲染帧逐像素一致
> （corr 0.99），与原生 Gyroflow 1.6.3 使用同一项目文件（initial_offset=0, do_autosync=false）
> 的导出无可见差别。用户已确认（2026-08-29）。
>
> 文中出现的 `demo.orv` / `demo/*.orv` 等工程文件与视频素材都是开发期样本，**不在仓库中**
> （真实赛事地图与个人素材不入库），复现时请自备。

---

## 0. 一句话结论（最重要的三条）

1. **DJI 视频必须关闭 autosync**（GPS 同步，真偏移≈0；rs_sync 会找到假 -3.6ms 偏移，反而放大脚触地高频振动）。
2. **预设文件必须全字段应用**（尤其 `smoothing_params`、`frame_readout_direction=TopToBottom`、`output.interpolation=Lanczos4`）。
3. **预览请求时间必须吸附到视频帧网格**（`round(t/dt)*dt`），否则墙钟时间的帧间偏移会在脚触地瞬间造成“一帧猛踢”——这是预览与导出观感不一致的最终根因。

---

## 1. autosync 风暴与假偏移（GUI 卡死 / 高频振动）

**现象**
- 早期 GUI 打开 `demo.orv`（`gyro.enabled=true`）后：满屏 AKAZE 日志（“Created non-linear scale space in 95s”），CPU 打满、硬盘 IO 风暴，用户复制文件都被卡住；UI 冻结、输入框无法输入。
- 导出视频在跑步脚触地段有明显高频振动（比原生 gyroflow 差）。

**根因**
- `start_gyro_load` 当时硬编码 `autosync=true`：`run_autosync` 会反复解码整段视频喂纯 Rust AKAZE 特征匹配（每秒级别的尺度空间构建 × 多窗口），这是后台线程，但疯狂抢 CPU/磁盘。
- rs_sync（offset_method=2）在特征匹配中找到一个 **-3.6ms 的假偏移**。DJI 视频内嵌出厂 GPS 同步的预融合四元数（真偏移≈0），应用这个假偏移反而把视频错位 3.6ms，在快速运动（跑步/脚触地）下被放大。

**修复**
- GUI 预览路径 `autosync=false`（见 `gui.rs` `start_gyro_load` 的注释）。
- `stabvid` 默认 `--no-autosync`，`--autosync` 手动开启（用于确实需要同步的素材）。

**验证（cv2 ECC MOTION_EUCLIDEAN，50–55s 跑步段）**

| 版本 | 残差 mean | 尖峰 |
|---|---|---|
| 原始 DJI | 6.62° | 66 |
| 开 autosync（-3.6ms） | 1.023° | 38 |
| 关 autosync（0 偏移） | **0.625°** | **22** |

**切勿回归**：任何情况下都不要把 GUI 预览的 autosync 改回 true；DJI 需要同步时只能走 CLI `--autosync`。

## 2. 预设必须全字段应用（apply_preset）

**现象**：早期导出“欠平滑”，用户点名「最大平滑度时间=2.5s、高速最大平滑度时间=1s」没生效。

**修复**：`gyro.rs::apply_preset` 必须与 gyroflow 本体的 preset 加载**逐项一致**：

- `fov`、`frame_readout_time`、**`frame_readout_direction`（TopToBottom，漏设 = RS 校正在错误轴上 → 高频横滚抖动）**
- `adaptive_zoom_method`、`adaptive_zoom_window`、`adaptive_zoom_center_offset`
- `lens_correction_amount`、`max_zoom` + `max_zoom_iterations`
- `video_speed` + `video_speed_affects_smoothing/zooming/zooming_limit`（读预设，勿硬编码 true）
- `additional_rotation`、`additional_translation`
- `method` → `smoothing.set_current(index)`（注意 "Default" 大小写：`position` 找不到时 fallback `1` 恰好是 DefaultAlgo，保持现状即可）
- **`smoothing_params` → 逐项 `set_parameter`**（smoothness=1.0、max_smoothness=2.5、alpha_0_1s=1.0、per_axis=0…）
- `horizon_lock_amount/roll` → `set_horizon`；`use_gravity_vectors`
- **`output.interpolation` → `stab.stabilization.write().interpolation = "Lanczos4".into()`**（预览/导出都走 Lanczos4，与原生一致）

**切勿回归**：删掉任何一条都会悄悄退回 gyroflow 默认值（默认平滑度 0.5/1.0/0.1），且**不会报错**。

## 3. 黑屏 / 全黑帧

**现象**：早期集成的稳定化输出全黑。

**根因与修复**
- `params.output_size` 未初始化 → `output_width=1` → fov=2284.8 → 全黑。必须在 `recompute_*` 之前 `set_size(w,h)` + `set_output_size(w,h)`（`load_stabilizer` 里已有，勿删）。
- warp 缩放重表达：当帧被缩放（解码缩放 / 预览下采样）时，单应必须用像素缩放矩阵 `S=diag(sx,sy,1)` 做 **`S·H·S⁻¹`**，**绝不能**用相机矩阵 K 做 `K·H·K⁻¹`（会把 K_orig·R·K_orig⁻¹ 再共轭一次 → 巨量平移 → 全黑）。

---

## 4. 稳定化四元数方向

**现象**：一度“防抖反而更抖”（0.237° vs 原始 0.19°）。

**根因/修复**：`q_rel = R_org · R_stab⁻¹`（`quat_mul(oq, quat_conj(sq))`），这样输出相机位姿 = R_stab（平滑）。方向反了会留下 R_org² 项。修复后输出位姿抖动 ≈0.03°。

## 5. previewPerf 陷阱（“导出好、App 里坏”的第一案发现场）

**现象**：导出视频完美，App 预览却是“没有防抖/很差”。

**根因**：用户测试时勾选了「预览高性能」，改动即自动应用把 **`previewPerf=true` 写进了 .orv**。而 `previewPerf=true` 的语义是：**预览跳过逐帧防抖 + 480p**（导出不受影响）——看起来就像预览没防抖。

**修复**
- `demo.orv` 重写为确定好的配置（`previewPerf=false`、`tailRenderMode=1`）。
- 防抖状态显示「已就绪（预览高性能：未应用）」明示跳过；窗口页复选框改名「预览高性能（跳过防抖，更快）」。
- **排查此类问题时先看 `[window] previewPerf` 和防抖页状态文字。**

## 6. 防抖加载触发规则 + 竞态

**规则（用户明确要求）**：启动/加载项目**不自动加载**防抖；只在 ①勾选「启用防抖」②防抖开启时换视频源 ③**点播放时**（后补）触发加载。

**竞态**：打开项目 → 异步 apply 未落地（1–2s）→ 点播放 → 当时的 `ensure_gyro_loaded` 因 `settings=None` 静默放弃 → 之后一直播原始视频。

**修复**
- `tick` 播放态每帧重试 `ensure_gyro_loaded`；
- `apply_prepared` 若用户已在播放则直接启动加载；
- 控制台打印 `[stab] auto-loading gyro (play-triggered)`。

## 7. GUI 线程饱和 → 异步预览 worker（丢帧 121–346/600 的根因）

**现象**：预览 `dropped 121~346 of last 600 frames`、拖动进度条极慢、GUI 卡顿。

**根因**：解码（pipe.get 有界等待）、`process_frame`、QImage 构建、绘制全部在 GUI 线程串行执行；加上地图原图 **6998×5055** 每帧软件 QPainter 旋转缩放绘制（约 35MP），GUI 线程每 tick 远超 16ms。

**修复（架构重构，与原生 Gyroflow 同思路）**
1. 独立 **预览 worker 线程**：独占 `PipeDecoder`/软解、执行 `process_frame`，产出 RGBA 到单槽（latest-frame）；
2. GUI 线程只 poll 槽、构建 QImage、画地图/路线/HUD（`decode_and_update` 已删除，勿恢复同步路径）；
3. **地图一次性降采样到 ≤1536px**（后台线程用 image crate Triangle 缩放），路线几何按同一比例 k 缩放：点/控制点/中点 ×k，分段 scale ÷k——数学一致（见 `compute_apply`）；
4. 拖动进度条：拖动只更新滑块 UI，**松手才 seek**；真实 seek 增加 generation 作废在途旧帧（`QML onPressedChanged` + `gui.rs seek`）。

**验收**：稳态丢帧 1–2/600。

## 8. 预览播放时钟：墙钟 + 帧网格吸附（最终根因）

**现象（最终一轮）**：三份差分导出（720p 处理/720p 输出、720p 处理/4K 输出、1440p/4K）**全部与 4K 完美版一模一样**，唯独 App 预览在脚触地有高频振动。

**根因**
- 导出：`t_ms = start + k·dt` 精确落在视频帧网格 → 四元数与帧内容严格同帧；
- 预览：`t_ms` 由墙钟驱动，落在网格之间（最多偏 ±8ms）。脚触地时相机角速度极高，±8ms 的“四元数 vs 帧内容”错位 = **一帧的猛踢**。
- （前奏 bug：t_ms 每 tick +dt，渲染慢时变成慢放——已改为墙钟 1×，慢时丢帧而非减速。）

**修复**
- 播放时钟 = 墙钟（`play_anchor_wall/play_anchor_t`，播放/seek 时重锚定，回环重置）；
- **worker 解码/防抖前吸附**：`t_snap = round(t/dt)*dt`，`pipe.get(t_snap)`、`process_frame(t_snap, fi)`、发布 `t_snap`——与导出逐字节同路径。

**切勿回归**：预览的时间绝不能直接使用墙钟原始值做防抖；必须先吸附帧网格。

## 9. 验证方法论与工具（复现用）

- **四元数对比**：gyroflow CLI `--export-metadata 3:<abs.json>`（`-b 0`；**绝对路径**，相对路径会 NotAFile；带 `--preset` 会先加载预设再导出，约 15s）。我们的 `stabvid --dump-quats <csv>` 输出 **稳定化相机位姿**四元数（注意：`smoothed_quaternions` 存的是修正四元数 `smooth⁻¹·raw`，需按导出同款公式 `(corr / org).inverse()` 反转）。`compare_quats.py` 对比：两者最大差 0.0002°。
- **像素对比**：`stabvid --dump-frames <dir>`（每 30 帧 PNG）+ 原生文件 ffmpeg 抽帧比对，corr 0.99。
- **ECC 残差**：`compare_stab.py <A> <B> <start> <dur>`（`-r 15` 而非 fps 滤镜，avbuild 无 fps filter）。**注意 ECC 对分辨率/编码敏感**：原生 4K 0.484° vs 原生 720p 重编码 0.738°——跨分辨率对比不可靠；且对 HEVC open-GOP 用两次 `-ss` 取帧会稳定早落一帧（是测量偏差，非文件丢帧；直接取第 0 帧验证 corr 0.966、两文件均 85237 帧、时长 1422.037s）。
- **已知事实**：DJI 文件 `per_frame_time_offsets len=0`、`lens_params len=0`（frame_idx 在导出/预览间差异无关紧要）；视频 PTS 网格 = k·1001/60000 从 0.000000 起无偏移。

## 10. 偏移调试旋钮（保留，默认 0）

- `gyro.offset_ms`（毫秒，旧）与 `gyro.offset_frames`（帧数，按 `1000/fps` 换算，优先）→ `gui::gyro_offset_ms(settings, fps)` 统一换算；
- GUI 防抖页「偏移帧数 (-5..+5)」；`stabvid --offset <ms>` / `--offset-frames <n>`；
- **DJI 最优 = 0**；±1/±2 帧、±1/±2/±3ms 均实测更差。默认保持 0，无需用户调。

## 11. 防抖加载进度条：从动画改成真实进度

**现象/需求**：加载运动数据时遮罩里只有一个 indeterminate 动画条，看不出还要多久；原生 Gyroflow 在加载运动数据时是有真实进度的。

**根因**：`load_stabilizer` 调用 `stab.load_gyro_data(...)` 时把进度回调写成了空实现 `|_p| {}`，而 gyroflow 本体（`controller.rs` 的 `loading_gyro_progress`）正是用这个回调驱动进度条。

**修复**
- `gyro.rs`：新增 `Phase` / `LoadProgress` / `ProgressSink`（`AtomicU64` 存 f64 位 + phase，无锁）与 `Progress<'a> = &'a dyn Fn(LoadProgress)`；
  `load_stabilizer` 末位参数改为 `progress: Progress`，把 `load_gyro_data` 的真实回调映射到 `[PROG_INIT_END, PROG_LOAD_END]`；
  `apply_seam_warmup_smoothing` 同样接收 sink（按段推进）。
- 阶段权重（实测 16 GB / 23 min DJI 冷缓存）：init 0.3s → 3%、motion-data 9.3s → 至 78%、preset 0.79、
  smooth 2.2s → 至 0.95、zoom 0.7s → 至 0.995、undistort ~0。**motion-data 占比最大且是唯一有真实字节进度的阶段**。
- `gui.rs`：`gyro_progress_slot: Option<Arc<ProgressSink>>`，loader 线程按段 `p.scaled(base, span)` 写入（多段时最后 10% 留给 seam warmup），
  GUI 每 tick `poll_gyro_progress()` 读取 → `gyro_progress` / `gyro_phase` 两个 Qt 属性；状态行显示「防抖: 读取运动数据 43%」。
- `gui.qml`：遮罩进度条 `indeterminate: item.busy || gyro_progress < 0`，否则 `value: gyro_progress` 并显示「阶段 + 百分比」；
  apply 阶段（无进度信号）仍走动画。

**为什么不"假爬"**：进度值只来自真实工作（telemetry-parser 扫描容器 metadata 流的字节偏移）。smooth/zoom 两个后处理阶段在
gyroflow_core 内部没有进度回调（要加就得改 `SmoothingAlgorithm::smooth` 的 trait 签名，代价大），因此**只显示阶段名**
（「计算平滑轨迹」）而进度条停在该阶段边界——诚实告知，不填充假数据。

**验证**：`gyrotest` 直接打印同一 sink；GUI 控制台每 10% 一行 `[stab] progress 43% (读取运动数据)`。实测 16 GB DJI：
`0% 初始化 → 3% 读取运动数据 → 13/24/33/47/53/66/74% → 79% 计算平滑轨迹 → 95% 计算自适应变焦 → 100%`。

**切勿回归**：不要把 `load_gyro_data` 的回调改回 `|_p| {}`；`Phase::ALL` 必须与枚举判别值顺序一致（`ProgressSink` 按判别值回查）。

## 13. 防抖预设与镜头标定（搜索框 + 拖放导入）

> 完整细节见 **`docs/防抖预设与镜头标定库.md`**（数据来源、实现、性能、目录约定）。这里只留要点。

- **不要只依赖 `.gyroflow`**：它只是「某个镜头标定 + 手改过的稳定化参数」的快照，换一台相机就不能用了。
  现在**设置页是唯一真源**：「视频」页新增的「稳定化」组把原版 Stabilization 面板那一整套
  （平滑方式+参数、视野、变焦方式/速度/上限/迭代/中心、镜头校正、地平线锁定、帧读出时间/方向、
  视频速度+联动、附加 3D 旋转/平移、陀螺偏移）都做成了**滑杆/数值框**（范围对齐原版，标签中文），
  **改完立即生效**；选中 `.gyroflow`（「预设文件」输入框）只是把它的 `stabilization` 段**填进**这些控件。
- 镜头标定用 Gyroflow 自带的**镜头库** `profiles.cbor.gz`（实测 **12409 条**：品牌/机型/镜头/分辨率），
  「镜头标定」搜索框里挑一条就换标定（稳定化参数不动），标定自带的帧读出时间会一并填进面板。
- 搜索框是**「输入即搜」**（对齐原版 `SearchField` + 结果弹窗；一万多条全列出来不现实）：
  空输入显示灰色占位「搜索...」，打字停下（180ms 防抖）就搜并**自动弹出**结果列表
  （条目标「官方/作者」），↑↓ 选择、回车确认。
- 预览区支持**拖放导入**：`.orv` 工程 / 视频 / 图片(地图) / `.gpx` / `.gyroflow` 预设 / `.json`(镜头标定)；
  **第一个视频/图片 = 主文件，之后再拖是追加**（续接分段 / 额外地图）。


**验证方式（无头/脚本）**：`& target\debug\tracereel-gui.exe 2>&1 | Tee-Object -FilePath run.txt` 能拿到 QML 的
`console.log` 与加载日志；**不要**用 `Start-Process -RedirectStandardError`（子进程没有控制台句柄时 Qt 的
assert 对话框会挂住主线程，QML 根本不执行）。另外 debug 构建链接的是 **Qt 调试运行时**（`Qt6Cored.dll`），
启动必弹一个 `Microsoft Visual C++ Runtime Library` / Debug Error 对话框：
`ASSERT: "bit < 2 * props" in ... qqmlengine.cpp, line 1441`（`QQmlData::growBits`）；
它与本次改动无关（去掉 PresetCombo 同样出现），点「忽略(&I)」即可继续，窗口正常显示。
用 release Qt 运行时不会弹（`run.ps1 -Release` 或发布版）。脚本里自动点掉：
`EnumChildWindows` 找到 `Button` 且文本含「忽略/Ignore」的句柄，`SendMessage(h, 0xF5 /*BM_CLICK*/, 0, 0)`。

**推荐直接用仓库里的 `.\verify_gui.ps1 -Orv demo\xxx.orv -Seconds 40`**：它把上面这套（Qt/ffmpeg 环境、
点断言框、收集输出）都封好了；再设 `QT_FORCE_STDERR_LOGGING=1` 就能把 QML 的 `console.log` 也收进来，
于是"临时在 QML 里塞个 Timer 打印 `item.gyro_status`/`item.gyro_stats`"就是最省事的内部状态验证法
（验证完记得删钩子）。

## 14. 「这个视频读不到防抖数据」——加载线程里的 `Duration` 溢出 panic

**症状**：某个 DJI 视频在原版 Gyroflow 里防抖正常（能看到运动数据），在本 App 里导入后
状态栏显示 **「防抖: 加载失败（请检查预设/视频，见日志）」**；同一台机器的**大文件反而正常**。
典型例子：一个 456 MB / 38.6 s 的 DJI 视频（同一台机器上更大的文件反而正常）。

**根因**：`app/src/gyro.rs::load_stabilizer` 末尾那段"阶段耗时"日志把**两个不同起点的
`Duration` 相减**。`t_init` 以 `t_phase` 为起点，而 `t_load_done`/`t_preset`/… 用的是
**加载开始后**才创建的 `t_load` 为起点 —— 于是 `t_load_done - t_init` 只要
「初始化阶段」（GPU + 镜头库 1.4–2.5 s + `init_from_video_data`）比「读运动数据」慢，
`Duration::sub` 就溢出 panic：

```
thread '<unnamed>' panicked at core\src\time.rs:1277:
overflow when subtracting durations
   6: tracereel::gyro::load_stabilizer   at .\app\src\gyro.rs:924
   7: tracereel::gui::impl$2::start_gyro_load::closure$0
```

panic 发生在**加载线程**里，`LoadDoneGuard` 照样把 `done` 置位，于是 `update_gyro_status`
判定"完成但没有 Stabilizer" →  latch `gyro_load_failed` → 状态栏「加载失败」。
**所有重活（读运动数据、平滑、变焦、去畸变）其实都成功了**，只是最后一行日志把线程带崩。

为什么"大文件正常"：17 GB 的文件读 `djmd` 运动数据要几十秒，`t_load_done` 反而大于 `t_init`，
巧合地不溢出。小文件 0.5 s 就读完 → 必崩。**凡是首次加载（镜头库还没进进程缓存）都会踩**。

**修复**：全部阶段计时统一到同一个起点 `t_phase`，并改用 `saturating_sub` 兜底
（这行日志绝不该有能力把加载线程干掉）：

```rust
let t_end = t_phase.elapsed();
eprintln!("[stab] phase timings: init {:.2}s | motion-data {:.2}s | ...",
    t_init.as_secs_f64(),
    t_load_done.saturating_sub(t_init).as_secs_f64(), /* ... */);
```

修复后实测（同一条视频）：`phase timings: init 2.53s | motion-data 0.55s | preset 0.01s | autosync 0.00s |
smooth 0.80s | zoom 0.51s | undistort 0.00s`，状态栏 **「防抖: 已就绪」**，
`gyro_stats={"pitch":40.82,"yaw":52.42,"roll":25.37,"zoom":100.0}`（真实最大旋转，不再是空值）。
用 `gyrotest.exe` 交叉验证：`gyro loaded: quats=38640 raw_imu=0 has_motion=true`。

**顺带修掉的浪费：运动数据被读两遍。** 启动/打开工程时 QML 的 `SmoothParams` 初始化会回写一次
`gyro_smoothing_params` → `apply_gyro_params`。`reusable` 要求 `!gyro_loading`，而此刻首次加载
正在途中 → 旧代码走"gyro-only reload"分支：**丢掉刚建好的加载、重读一遍运动数据**（日志里两条
`gyro load finished in ~5s`，大文件上白白多等一倍）。现在改成：在途加载时**排队**
（新字段 `pending_gyro_apply`），等这次加载真正落地（含分段缝合预热）后由 `update_gyro_status`
触发一次**分级重算**把新参数应用上去；加载失败或完整 apply 落地则丢弃这条排队。
实测：`gyro load finished in 4.4s`（只有一次）+ `re-applied 'gyro_smoothing_params' to 1 segment(s) in 1.36s`，
最终 `gyro_stats` 与旧路径**逐位相同**。多段（2 段）同样验证通过：一次加载 + `re-applied ... to 2 segment(s)`。

> 教训：**后台线程里任何 `panic!`（含 `Duration`/索引这类"顺手写"的算术）都会静默变成用户看到的
> 功能性失败**（"加载失败"），因为加载线程死了但 `done` 标志仍会置位。诊断入口就一句
> `RUST_BACKTRACE=1` 跑一遍，日志里的 backtrace 直接指到行号。
